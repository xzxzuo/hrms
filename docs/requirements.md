## 三、核心业务功能

### 1. 用户与权限模块

实现用户注册、登录、JWT 认证、角色授权、密码加密、个人信息和订单查询。

至少设置 USER、HOTEL_MANAGER、ADMIN 三类角色。酒店管理员只能管理授权酒店的数据，避免水平越权和垂直越权。

### 2. 酒店与房型管理

实现酒店创建、修改、上下架、城市及条件检索、酒店详情、房型、设施、图片元信息等。

房型应包含名称、床型、容纳人数、基本价格、房间数量与状态。

区分房型库存和具体物理房号，不要把两者混为一谈。

### 3. 日期库存管理

这是系统最重要的模块之一。

酒店的库存需要采用**房型 + 日期**的建模方案。

例如用户入住 11 月 1 日、11 月 4 日离店，需要占用 11 月 1、2、3 日的库存，而不包含 11 月 4 日。

为每个房型、每个日期维护独立库存记录。

至少考虑：

- total：总库存。
- available：可售库存。
- held：已锁定但未支付库存。
- sold：已确认预订的库存。
- sale_status：是否允许销售。

需要明确定义库存不变量，处理维修停用、房间停售、增加房量、退订回补等情况。

要求实现跨日期原子扣减：只要其中一个日期库存不足，整笔预订失败，不能部分占用库存。

### 4. 订单模块

实现完整预订链路：

酒店检索 → 房型选择 → 日期选择 → 库存查询 → 价格计算 → 下单 → 库存锁定 → 待支付 → 支付成功 → 预订确认 → 入住 → 退房。

支持用户取消订单、后台取消订单和超时自动取消。

订单状态至少包括：

PENDING_PAYMENT、CONFIRMED、CANCELLED、EXPIRED、CHECKED_IN、CHECKED_OUT。

要求设计状态迁移表，明确每种操作所允许的原状态、目标状态及库存变动。

通过数据库条件更新、事务和唯一约束保证幂等性，禁止非法状态转换。

### 5. 支付与退款模块

使用可控的模拟支付网关，而不是真实支付接口。

模拟用户支付、支付成功回调、重复回调、支付失败、订单超时、退款申请和退款完成。

支付回调应有开发环境可验证的签名或身份校验机制。

必须重点解决支付成功与订单超时关闭同时发生时的竞态条件，不能出现订单取消但仍被确认为已支付、库存被重复释放的问题。

### 6. 优惠券与营销

实现优惠券创建、领取、使用、过期、订单取消后的处理。

使用数据库唯一约束防止重复领取或重复使用；考虑优惠券状态与订单状态的一致性。

### 7. 高并发限时秒杀

实现指定酒店、房型、入住日期和活动数量的限时秒杀。

需要覆盖：

- 活动开始前不允许抢购。
- 活动结束后拒绝请求。
- 用户身份验证。
- 活动库存有限。
- 单用户限购。
- 高并发请求。
- Redis Lua 原子准入。
- RabbitMQ 异步处理。
- 消费端幂等。
- MySQL 最终库存校验。
- 秒杀成功、失败、排队状态查询。
- 订单超时释放库存。
- 消息重复与异常补偿。

**活动配额与真实房型每日库存必须分开设计。Redis 预扣成功只能代表准入，不能代表实际预订成功。**

### 8. 后台运营模块

酒店管理员可以查看和修改每日房量、房价、酒店上下架状态、订单状态及营销活动。

管理员可以查看基础经营报表，例如每日订单数量、入住率、销售额及取消率。

### 9. 系统监控与审计

监控请求吞吐量、响应延迟、缓存命中率、数据库连接池、订单异常、MQ 堆积、重试和死信队列。

记录库存操作流水、订单状态变化和重要管理操作，确保问题能够被追踪。

## 四、MySQL 数据库设计

至少包含以下表：

users、roles、user_roles、hotels、room_types、room_daily_inventory、room_daily_rate、bookings、booking_nights、inventory_ledger、payments、refunds、coupons、user_coupons、seckill_campaigns、seckill_requests、outbox_events、processed_messages、audit_logs。

根据需要补充其他表。

要求：

1. 绘制 ER 图，明确实体关系。
2. 输出完整建表 SQL 与 Flyway Migration。
3. 说明字段含义、数据类型、主键、外键、唯一索引和复合索引。
4. 提供典型 SQL、查询执行计划 EXPLAIN 和索引优化分析。
5. 所有金额使用 BigDecimal/DECIMAL，订单保存价格快照。
6. 对订单幂等键、支付流水号、消息处理 ID 设置恰当唯一约束。
7. 明确事务隔离级别、锁顺序、死锁重试及异常处理。

重点分析房型日期库存表设计，以及为何不同日期的库存必须同时扣减。

## 五、高并发预订与防超卖

普通下单时，MySQL 是最终库存权威数据源。

客户端生成稳定的 clientRequestId，服务端使用 userId + clientRequestId 保证幂等。

必须实现一个完整的数据库事务，在同一事务内：

1. 校验订单和报价的有效性。
2. 创建订单。
3. 按日期升序锁定每晚库存。
4. 通过条件 UPDATE 扣减 available、增加 held。
5. 检查每条更新的 affectedRows。
6. 创建订单入住夜记录。
7. 写入库存流水。
8. 写入 Outbox 事件。
9. 统一提交或回滚。

建议使用如下条件更新思想：

`UPDATE room_daily_inventory SET available = available - ?, held = held + ? WHERE room_type_id = ? AND stay_date = ? AND available >= ? AND sale_status = 'OPEN'`

任何一个日期扣减失败，事务必须全部回滚。

不得仅通过先 SELECT 再无条件 UPDATE 处理并发。

需要解释 MySQL 行锁、原子条件更新、乐观锁和分布式锁的区别，以及为何不应依赖 Redis 锁保证数据库库存的最终正确性。

支付成功时 held 转 sold；待支付订单取消或超时时 held 转 available；已确认订单取消时根据业务取消规则正确回补库存。

## 六、Redis 缓存设计

使用 Cache Aside 模式缓存酒店详情、房型静态信息、热门酒店和部分查询结果。

要求设计 Redis Key 命名、数据结构、TTL、随机过期时间、缓存更新策略与异常降级方案。

覆盖以下缓存问题：

- 缓存穿透：空值缓存及必要时的 Bloom Filter。
- 缓存击穿：热点 Key 重建保护。
- 缓存雪崩：随机 TTL、限流和降级。
- 缓存一致性：数据库更新后失效缓存，分析失败重试及竞态窗口。
- 热点房型：高频查询与有限库存的分离。

库存展示可以缓存，但订单创建时必须重新进行权威库存验证。

给出使用缓存前后的性能对比方法，不能编造缓存命中率或 QPS。

## 七、RabbitMQ 异步消息系统

设计可靠的消息处理链路，至少支持异步订单处理、支付成功后通知、订单超时取消、秒杀消息、库存对账和异常重试。

必须采用事务性 Outbox 或同等级可验证的可靠发布机制。

业务状态变化与待发送事件必须在同一个 MySQL 事务提交。

要求实现：

- Publisher Confirm。
- Consumer Manual ACK。
- 消息持久化。
- 重复消费幂等。
- 有界重试及退避。
- Dead Letter Queue。
- 失败告警。
- Outbox 重试投递。
- 业务对账与异常恢复。

明确 MQ 是至少一次投递模型，业务层通过唯一约束和幂等处理实现可靠结果，而不是假设 RabbitMQ 能提供跨数据库的 exactly-once 事务。

## 八、秒杀链路具体实现

设计以下完整调用链：

用户请求 → API 限流与鉴权 → 活动有效性检查 → Redis Lua 原子准入 → MySQL 持久化秒杀请求和 Outbox → RabbitMQ 异步消息 → 消费者校验 → MySQL 活动配额及每日库存条件扣减 → 创建订单 → 更新秒杀结果 → 用户查询结果。

需要明确：

1. Redis Lua 如何原子检查活动额度与用户参与资格。
2. 多 Key Lua 在 Redis Cluster 下如何处理 Hash Slot。
3. Redis 预扣与数据库真实库存不一致时如何补偿。
4. Redis 扣减成功但数据库持久化失败时如何恢复。
5. RabbitMQ 宕机或消息投递失败时如何恢复。
6. 消费者异常退出或消息重复投递时如何避免重复扣减。
7. Redis 准入记录丢失如何根据权威数据重建。
8. 同一用户重复抢购如何返回稳定结果。
9. 活动配额耗尽但真实房量尚有剩余时应如何处理。
10. 订单未付款释放库存后是否返还活动配额，需明确业务规则。

提供 Lua 脚本、Java 调用代码、消息消费者、数据库 SQL 以及完整的并发测试。

**核心验收：成功订单数量不得超过活动配额或任何入住夜的实际可售库存。**

## 九、订单超时取消

设置待支付订单有效期，例如 15 分钟。

采用 RabbitMQ 延迟处理与数据库定时扫描兜底。

消息触发后必须重新查数据库订单状态及过期时间，只有满足条件才关闭订单及回补库存。

如果订单已经支付，不得取消或重复释放库存。

重点测试支付回调、用户取消、超时任务三方并发竞争的情况，要求状态变化与库存变更在同一事务内完成。
